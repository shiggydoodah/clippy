# CLAUDE.md

Guidance for Claude Code when working in this repository.

## Project

**Clippy** — a lightweight macOS clipboard history manager with favourites. Menu bar resident, keyboard driven, entirely local.

**This file is the only guidance document.** Module boundaries, hard rules and conventions are all below. For anything not covered here, the code is the source of truth: the data model in `Clippy/Storage/Item.swift` and `Migrations.swift`, the settings in `Clippy/Settings/AppSettings.swift`, the keyboard map in `Clippy/Panel/PanelController.swift`.

---

## Stack

- **Swift 5.9+**, targeting **macOS 14+**
- **SwiftUI** for view content, **AppKit** for windowing and the status item
- **GRDB** for SQLite
- **KeyboardShortcuts** (sindresorhus) for global hotkeys
- **SMAppService** for launch at login (system framework — do not add a package for this)

### Dependency policy

The allowed third-party packages are **GRDB** and **KeyboardShortcuts**. That is the complete list.

Do not add any other dependency without asking first. If a task seems to need one, propose it and explain what it replaces — a system framework is almost always available.

---

## Hard rules

1. **No networking.** The app makes zero outbound connections. Do not add URLSession, analytics, crash reporting, update checkers, or telemetry of any kind.
2. **Never persist concealed pasteboard content.** Items marked `org.nspasteboard.ConcealedType`, `TransientType`, or `AutoGeneratedType` are skipped before any storage path. This is a correctness requirement, not a feature.
3. **Favourites are exempt from all retention rules.** Never prune a favourite by age, count, or size.
4. **Use AppKit for the panel.** `NSPanel` with `.nonactivatingPanel`. Do not substitute SwiftUI `MenuBarExtra` or `Window` — they cannot control focus and window level the way this app needs.
5. **Never block the main thread.** Pasteboard polling, classification, hashing, and blob writes all run on background queues.

## Conventions

### Structure

```
Clippy/             (source root — the Xcode project and targets are named Clippy)
├── App/            ClipApp.swift, AppDelegate, StatusItemController
├── Clipboard/      ClipboardMonitor, ItemClassifier, PasteService
├── Storage/        StorageService, Migrations, Item model, BlobStore
├── Retention/      RetentionEngine
├── Panel/          PanelController, and SwiftUI views in Panel/Views/
├── Settings/       SettingsWindow, Settings model, per-pane views
└── Shared/         Extensions, small utilities
```

One type per file, filename matches the type. Keep modules from reaching across boundaries — `PanelController` talks to `StorageService`, not to `ClipboardMonitor`.

### Style

- Prefer `struct` over `class` unless reference semantics or AppKit inheritance is required
- `async/await` over completion handlers; use `actor` for shared mutable state
- Explicit access control — `private` by default, widen only when needed
- No force unwrapping (`!`) outside of tests and `@IBOutlet`-equivalent lifecycle points
- No force try (`try!`) — handle or propagate
- British spelling in user-facing strings and type names (`Favourite`, not `Favorite`) — be consistent, the DB column names depend on it

### Comments

Comment _why_, not _what_. The AppKit windowing code and the pasteboard polling loop both contain non-obvious workarounds — those deserve a comment explaining the constraint. Straightforward SwiftUI does not.

### Errors

Use typed errors (`enum StorageError: Error`). Log failures with `os.Logger`, subsystem `com.clip.app`. Never fail silently in the capture path — a dropped clipboard item the user expected to be saved is a bug they will notice and struggle to reproduce.

## Working style

**Explain Swift decisions.** This codebase is maintained by someone who works in TypeScript/React day to day, not Swift. When choosing between `@State`/`@StateObject`/`@Observable`, or between `NSWindow` and `NSPanel`, or reaching for an actor — briefly say why. Comparisons to TS/React idioms are useful where they genuinely map, and misleading where they do not; skip the analogy if it does not hold.

**Prefer boring solutions.** This app should be readable in six months. No clever abstractions, no premature protocol-oriented layering, no generic wrappers around single call sites.

**Do not optimise pre-emptively.** Everything should be written the simple way first. There are only three real performance hazards, and they are already handled — do not undo them:

- **Preview building must stay bounded.** A clip can legally be megabytes of text. Building its one-line preview, or the preview-pane excerpt, must cost O(limit) and never O(length) — see `String+PreviewCap.swift` and `ClipboardMonitor.preview`. Do not replace the index walks with `count` or `prefix`.
- **Image thumbnails must stay lazy.** Never decode a 4K screenshot into an `NSImage` at capture time. Store raw data, build the thumbnail on first display, cache it in an `NSCache`.
- **The poll timer must stay cheap.** It reads one integer and compares. Classification and filtering happen only after a change is detected — never in the polling path.

Note that the size threshold deliberately does **not** walk copied folders. File captures are stored as path references, so their `byteSize` is the path string and they are effectively exempt from the limit. Measuring a copied folder's true size means a directory traversal on the capture path; if you ever add it, it belongs on a background queue with depth and file-count caps and an early bail-out once the running total exceeds the threshold — the exact size is never needed.

Targets: under 60MB resident and under 0.1% CPU when idle, panel summon to first paint under 100ms, text capture to stored under 50ms.

**When something in this file is wrong or unworkable, say so.** If an AppKit API does not behave as described here, flag it rather than silently working around it.

## Commands

```bash
# Run from the repo root (where Clippy.xcodeproj lives)

# Build
xcodebuild -scheme Clippy -configuration Debug build

# Test (unit tests only — the UI test targets are untouched template stubs)
xcodebuild -scheme Clippy -destination 'platform=macOS' -only-testing:ClippyTests test

# Run (after build)
open ~/Library/Developer/Xcode/DerivedData/Clippy-*/Build/Products/Debug/Clippy.app

# Watch the app's log (use the full path — zsh shadows `log` with a builtin)
/usr/bin/log stream --predicate 'subsystem == "com.clip.app"'
```

Prefer `xcodebuild` output over asking the user to check Xcode manually.

## Testing

Unit tests for the parts with real logic:

- `ItemClassifier` — kind detection across representative payloads
- `StorageService` — dedupe by hash, blob write/read, ephemeral mode
- `RetentionEngine` — max item count, max age, orphaned blob sweep, plus the favourite exemption on all three
- Filter rules — excluded extensions, folders, apps, size threshold

Do not write tests for SwiftUI view bodies or AppKit window configuration. Those are verified by running the app.

---

## Manual verification checklist

After any change to the capture path, confirm by hand:

- [ ] Copying text, a URL, an image, and a file each produce the correct `kind`
- [ ] Copying a password from a password manager stores **nothing**
- [ ] Copying the same content twice does not create a duplicate row
- [ ] Panel appears over a fullscreen app
- [ ] Panel does not steal focus — the app underneath stays active
- [ ] Hold ↓ through a history containing a large (100KB+) text clip — the selection highlight stays visible and on-screen the whole way, with no stutter (no automated seam for this; the scroll behaviour only exists in the running app)
- [ ] Idle memory under 60MB in Activity Monitor after 10 minutes
